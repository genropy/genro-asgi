# Context: wf/33-reboot
Parent: develop
Mode: interactive

## Objective

Give the server a **reboot**: a **soft quit** that photographs the live
population on the way out, and a **soft start** that adopts it on the way in.
The urgent case is development — one developer on his Mac, `genroasgi serve
--reload`, who must stop re-logging in at every save of a source file.

Vocabulary, dictated by the owner (2026-08-25): there is a **reboot**, which
has a **soft quit** and a **soft start**. "Soft boot" is not said.

Authority order on any doubt: `temp/decisioni_registri_cancello_2026-08-25.md`
(this conversation's record — the sequence, the two directories, the cut, who
commands) > `temp/interview_handler_2026-08-15.md` (E8, F1-F5) >
`temp/liturgia_riavvio_orientamenti_2026-08-20.md` > this plan.

**Issue #33 is NOT the design.** It reports that the reboot is missing, and
that is all it is worth. Its versioned *boot manifest* contradicts F4 (nothing
derivable is ever saved; the indexes are regenerated by scanning the photo) and
F5 (the commit is the atomic rename — no marker, no version stamp). Its three
"open questions for the owner" are already answered in the register: F3 (the
reboot directory), F2 (every start that is not the deliberate liturgy is HARD,
so this is not opt-in).

**Out of scope, declared.** The deliberate reboot command under `_server`
(`reboot now` / `reboot wait N`), the notice to the users, `notify_user`, the
service-message lane to the consumer (designed in
`temp/decisioni_registri_cancello_2026-08-25.md` §4quinquies, **not built**),
the restart of a single worker, the stream registry, and `execv`. This
workflow ends with the process dying and the next one adopting.

**Naming rule.** A new public name whose baptism is not settled is born with
the `_TBD` suffix. At the END of each phase this chat brings the owner ONLY the
surviving `_TBD` names — one at a time, semantics plus 2-3 candidates — and the
rename is a search-and-replace in its own commit. No `_TBD` survives the end of
the workflow.

**Already baptised by the owner**: `reboot_temp` (the directory written during
the quit) and `reboot_data` (the same directory after the rename).

**Expected `_TBD` at birth**:
1. the server's gate — close, open, and the wait for the drain;
2. the order the commander sends the groups and the groups send the workers
   ("we are closing");
3. the module constant of the per-user grace (~5 seconds).

## The decisions this plan stands on

**D-a. The strong transport rule** (owner, 2026-08-25). The transport decides
nothing. Whatever the channel, the server acts if and only if: whoever asks
carries the tags, the server has the capability, the operation is admitted on
that channel. And: a request is in flight from the moment it is taken in charge
to the moment it is answered on its own channel. Consequence that binds this
work: **the unit registered is the request taken in charge, never the
connection** — on HTTP the two coincide, on WSX one socket carries many.

**D-b. Three species, three treatments** (owner, 2026-08-25). Requests live in
`RequestRegistry`. Streams do NOT go in the same registry and will get their
own when they are dealt with. Static and one-shot (favicon and the like) are
served without being registered — which already happens today for whatever the
middleware chain answers itself (`MiddlewareMixin.__call__`,
`middleware/__init__.py:107`, sits above `BaseServer.__call__` in the MRO, and
registration happens only at the innermost point, `server.py:196`).

**D-c. The gate sits where the registration sits** — never welded into the
`http` branch. One rule, two effects: what is registered is what is held, what
the chain serves earlier is neither. Welded into the `http` branch, the WSX
motor would be born outside the gate and the A1 divergence
(`SPECIFICATION.md:701`, Q1) would repeat.

**D-d. The soft quit sequence** (owner, 2026-08-25): gate closed → the groups
told, and through them the workers → every worker writes its users into
`reboot_temp` and closes them one by one, each as his last call ends → whoever
arrives gets 503 → the commander sees everybody done, adds its own part →
rename → the process dies.

**D-e. The cut** (owner, 2026-08-25). A worker's blocked calls are closed with
503 after a few seconds. Two reasons: every request gets a real answer instead
of hanging until the process dies under it; and **cutting is what unblocks the
freeze** — a stuck call keeps the user's pendings above zero, so he cannot be
frozen. Consequence: the drain never hangs, `in_flight` reaches zero by
completion or by cut.

**D-f. Two levels of ownership.** The server owns the gate and the registry and
cannot delegate them: requests arrive at the server, and a server may host
applications that have nothing to do with the SPA. The population belongs to
the SPA application through its commander, and nobody else can freeze it. The
lifecycle hook is on the application contract, symmetric with the existing
`on_startup`/`on_shutdown` (`spa_app.py:277`).

**D-g. The rename is the commit** (F5). Written under `reboot_temp`, renamed to
`reboot_data` by the commander as its last act. A crash halfway leaves
`reboot_temp`, which the soft start never looks at.

**D-h. The commander pickles its own registers** (owner, 2026-08-25) — this
SUPERSEDES F4 for this case. The maps go into the photo beside the global
store, in the same act. The reason is the cookies: the chain is cookie -> cid
-> user, and the single point where it lives or dies is `resolve_user(cid)`
(`spa_commander.py:1032`), which reads `connection_user_map`. Empty map ->
`resolve_user` returns None -> the site mints a new connection, the front
rewrites the cookie, the user logs in again — exactly what this work exists to
prevent. Without the saved maps the only ways back from cid to user were
reading the filenames backwards — forbidden by `user_to_userkey`
(`freeze_handler.py:92`), and `cleanup_frozen` (:301) is built on that ban — or
losing the cookies. So the indexes are NOT derivable here.

Coherent with the register, not a derogation: F4 feared divergence between two
sources written at different moments, and F5's rename removes that window (maps
and parcels are made visible together, or not at all); and the gift that
justified the scan was crash recovery (E8), which **F2 revoked**. With that
gone the scan buys nothing the pickle does not, and costs one unpickle per
parcel — group and age live inside the files (`get_item_header` goes through
`_read_envelope`, :339).

Two things stay true: the indexes are saved ONLY inside the photo, never in the
working folder, so a crash leaves nothing to believe; and an unreadable pickle
discards the WHOLE photo and boots hard — never a partial adoption.
Consequence: `user_to_userkey` stays ONE WAY untouched and no folder scan is
written.

**D-i. Two renames, each meaning something.** At the quit `reboot_temp` ->
`reboot_data` = "the photo is complete". At the soft start `reboot_data` -> the
working folder = "the photo is taken in charge, ordinary state from here". The
second is what reuses the existing machinery instead of writing new: after it
the lazy wakes read the working folder as they always have, and the workers'
`FreezeHandler` is the usual one. It also satisfies F4's "delete the reboot
directory after using it" without deleting anything — the name disappears
because it became the other one. The FIRST rename may NOT land directly on the
working folder: that would remove the only signal telling soft from hard
(`reboot_data` present = complete photo, absent = hard, F2/F5), and a crash's
leftovers would look exactly like a governed photo.

**D-j. The hierarchy, and the bundle** (owner, 2026-08-25):

```
server
  spa application
    group -- bundle
```

A group of an SPA runs a **bundle**. The term is already in use —
`codex/progetto-distribuzione-bundle-applicativi-s3-2026-08-20.md`: "A live
group is pinned to a resolved immutable bundle" (:76), and it separates the
worker runtime, common to every bundle (:153), from the bundle itself. This is
the frontier that answers the development case: the **runtime** changes ->
restart the server; the **bundle** changes -> restart that group. Development
and production are not two mechanisms — in production a new bundle version
arrives, in development the developer edits the bundle in place. Same remedy,
different triggers.

**D-k. A group reboot needs no photo.** If one group goes down the commander
does NOT die, so its maps are in memory: no photo, no `reboot_temp`, no rename,
no global store to save. Only freezing that group's users into the WORKING
freezer, restarting the processes, and letting the lazy wake bring them back.
The whole photo machinery exists for one reason — **the commander dies**. Where
it does not, it is not needed. The restart primitive already exists
(`GroupHandler.restart_worker`, `group_handler.py:438`); the trap is the
template process, which froze its heap on the old bundle and must be remade
first. NOT built here: recorded so this workflow is not written in a way that
makes it a second implementation.

**D-l. All the triggers run the same sequence.** The deliberate command on
`ServerApplication` (orientations §2, not built here), the shutdown the
supervisor sends under `--reload` (built here), and one day the watcher that
classifies the changed path. The classifier does not exist and is not trivial:
uvicorn does not say what changed. And today the situation is inverted —
`reload_dir` (`__main__.py:304`) watches the directory of the source file given
to the CLI, i.e. the `config.py`'s, so `--reload` fires on BUNDLE code and
rebuilds EVERYTHING, and does not fire on genro-asgi's own code at all. Scope
decided: this workflow reboots the whole server on any change. Development
works from day one — no re-login — at the cost of a bigger restart than needed.
